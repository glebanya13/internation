# Система учёта студентов и дежурств

Стадия: **M6 — веб-админка.** Система готова к развёртыванию на VPS.
Целевой цикл работает целиком через интерфейс: вход администратора →
этажи → комнаты и блоки → состав этажа → импорт XLSX с diff →
генерация графика → просмотр → экспорт PDF/XLSX → публикация →
дежурства → выполнено / пропущено / замена → пропуски и объяснительные.

**AI в системе отсутствует.** Ни API, ни LLM, ни зависимостей —
за этим следит `tests/invariants/no-ai.test.ts`.

Проектная документация:

- [Разбор исходных документов](docs/duty-system-design.html) — что реально есть в бланках
- [Спецификация](docs/duty-system-spec.html) — модель данных, алгоритмы, роли, экспорт

## Архитектурные правила, зафиксированные в коде

**Структура ≠ заселение.** `rooms` и `blocks` описывают, какие помещения
существуют. Кто в них живёт — определяет `roster`. Поля вместимости нет
и не будет: число проживающих это `COUNT(*)` по `students`, и ноль
является валидным значением.

**Roster — источник истины для генерации.** Кандидаты берутся только из
текущей подтверждённой версии состава (`roster_versions.status = 'confirmed'`).
Обхода комнат в пайплайне нет: пустая комната, пустой блок и пустой этаж
просто не дают кандидатов.

**Изоляция этажей — свойство схемы.** Составные внешние ключи
`students(room_id, floor_id) → rooms(id, floor_id)` и
`duty_schedules(roster_version_id, floor_id) → roster_versions(id, floor_id)`
делают межэтажное смешение невыразимым на уровне БД, а не только запрещённым
в сервисах.

**Состав против атрибутов.** Разделение задано в
[`src/domain/roster.ts`](src/domain/roster.ts):

| Создаёт новую версию roster | Идёт в `audit_log` |
| --- | --- |
| заселение, добавление на этаж | опечатка в ФИО |
| переселение в комнату или блок | факультет |
| перевод на другой этаж | курс, группа |
| деактивация, выселение | учебная смена |
| импорт, изменивший состав | Telegram ID |

**Прошлое неизменяемо.** `roster_entries`, `duty_changes` и `audit_log`
доступны только для вставки — это триггер, а не соглашение. Опубликованный
график хранит `roster_version_id` и снимки ФИО, комнаты и этажа, поэтому
переезд, перевод и переименование факультета его не меняют.

**Данные против кода.** Этажи, факультеты, учебные смены, шаблоны смен
и правила распределения — строки в таблицах. ENUM остались только там, где
новое значение требует новой логики: статусы студента, графика, дежурства,
нарушения и роли.

## Генератор графика

Детерминированный, без случайности и без AI. Одни и те же roster, месяц,
настройки и шаблон смен дают побайтово одинаковый результат: все сравнения
имеют устойчивый tie-break по `studentId`, порядок обхода слотов фиксирован.
`seed` выводится из входных данных и записывается в историю прогонов.

Порядок: hard-ограничения соблюдаются всегда → soft-предпочтения
оптимизируются → если слоты всё равно не закрываются, ослабляются
настраиваемые пороги, и каждое ослабление попадает в метаданные прогона
и в предупреждения.

| Hard — не ослабляется никогда | Soft — оптимизируется |
| --- | --- |
| другой этаж | равномерность нагрузки |
| нет в подтверждённом составе | два дежурства в один день |
| студент неактивен | смены подряд |
| пересечение по времени | интервал между дежурствами |
| запрещённое учебное время | баланс по типам смен |
| слот уже занят | перенос баланса с прошлого месяца |
| дата вне месяца | разнообразие дней недели |
| | разнообразие пар «день + смена» |

### Разнообразие без случайности

При малом числе студентов график вырождался в жёсткую недельную ротацию:
7 студентов × 4 смены = 28 назначений = 7 дней × 4, состояние после каждой
недели повторялось, и жадный выбор воспроизводил ту же расстановку —
один человек получал вторник 09:00 все четыре недели.

Лечится двумя счётчиками в состоянии генератора: сколько раз студент уже
получал этот день недели и эту пару «день недели + смена». Штраф за пару
квадратичный (`n² × 90`), поэтому четвёртый повтор дороже лишнего дежурства
и не случается, а первые два не мешают балансу. Случайность не нужна:
счётчики — часть детерминированного состояния, три прогона подряд дают
одинаковый sha256.

Замер на сентябре 2026 (версия генератора v2):

| Студентов | Разброс нагрузки | Макс. повтор пары | Уникальных пар |
| --- | --- | --- | --- |
| 5 | 0 | 2 | 23.6 |
| 7 | 1 | 3 | 13.7 |
| 12 | 0 | 1 | 10.0 |
| 25 | 1 | 2 | 4.8 |

Полное покрытие всех семи дней недели не гарантируется: приоритет
у равномерности, и ради лишнего дня алгоритм не станет портить баланс.

## Telegram-бот и уведомления

```
Telegram Bot (adapter) → BotService → Application Services → PostgreSQL
NotificationService → TelegramNotificationAdapter
Scheduler (worker) → NotificationService
```

Бизнес-логики в Telegram-хендлерах нет: адаптер превращает текст сообщения
в действие и отправляет обратно то, что вернул `BotService`. Отдельный тест
проверяет, что в `src/adapters/telegram/` не встречается ни обращений к базе,
ни предметной логики, ни cron.

**Безопасность.** Единственный вход — `telegram_id` из самого обновления
Telegram. `BotService` не принимает `student_id`, `floor_id` или
`schedule_id` снаружи: подставить чужой идентификатор некуда, параметра
не существует. `/floor 7` распознаётся как неизвестная команда.

**Два счётчика пропусков.** В сообщении студенту — все зафиксированные
пропуски, включая только что отмеченный. Порог объяснительной считается
отдельно и только по подтверждённым администратором: между «пропущено»
и «нарушение» всегда стоит решение человека.

**Идемпотентность.** Уникальный индекс на
`(студент, дежурство, нарушение, замена, тип)` гарантирует, что напоминание
и уведомление уходят ровно один раз, сколько бы раз ни просыпался
планировщик. Сбой канала не теряет сообщение: до пяти попыток, затем
`failed`.

Отметку выполнения делает администратор. Самоподтверждения, геолокации,
фото и QR нет намеренно.

### Разграничение доступа

| Роль | Область |
| --- | --- |
| `superadmin` | все общежития и этажи |
| `dorm_admin` | своё общежитие целиком, справочники |
| `floor_admin` | только этажи из `admin_floor_scopes` |

Область видимости задаётся **списком этажей**, а не номерами в коде.
Каждый обработчик, работающий с данными этажа, начинается с `context()`
или `assert*Access()`: идентификатор чужого этажа в запросе возвращает
403, а не чужие данные. Подстановка `?floor=<чужой>` просто показывает
свой этаж.

### Настройки

Через интерфейс редактируются: факультеты, учебные смены и их время учёбы,
этажи, шаблоны смен и время каждой смены, порог пропусков, период их
подсчёта, время напоминаний, параметры печати. Правка кода для этого
не требуется нигде.

### Защита от публикации по устаревшему составу

Перед публикацией показывается подтверждение: этаж, месяц, число студентов,
число дежурств. Если состав этажа изменился после генерации, публикация
блокируется — снять блокировку можно только явной отметкой «публиковать
по прежнему составу». Случайно опубликовать график, где половина студентов
уже выселена, нельзя.

## Два источника списка, которые нельзя смешивать

`FloorRosterQueryService` — **текущее состояние**. Один SQL-запрос, одно
согласованное состояние: комната, блок, ФИО, факультет, смена, курс и группа
читаются из одного снимка транзакции. Состав берётся из `students`, а не из
`roster_entries`, поэтому исправление факультета видно немедленно. Номер
версии в `meta` — подпись документа, а не источник строк.

`RosterSnapshotQueryService` — **исторический снимок**. Читает только
`roster_entries`, без единого соединения с `students` и справочниками.
Студент перешёл с ФИТ на ТОВ — старый список по-прежнему показывает ФИТ.

Оба возвращают один DTO `FloorRoster`, поэтому рендереры общие.

**Известное ограничение снимка:** пустые комнаты в исторической версии
недоступны — снимок хранит людей, а состав помещений на тот момент нигде
не зафиксирован. Достроить их из текущей структуры значило бы смешать
состояния внутри одного документа, поэтому `meta.emptyRoomsAvailable = false`.
