Шесть принципов, из которых следует всё остальное

  1. Структура ≠ заселение. Комнаты и блоки описывают, какие помещения существуют. Кто в них живёт — определяет только актуальный roster. График строится исключительно по roster, никогда по структуре. Развёрнуто ниже ★
  2. Изоляция этажей — свойство схемы, а не UI. CHECK-ограничение связывает этаж студента с этажом его комнаты; сервисы всегда фильтруют по floor_id; бот берёт этаж из карточки, а не из сообщения.
  3. Ничего не удаляется. Деактивация вместо удаления, ON DELETE RESTRICT там, где есть история.
  4. Прошлое неизменяемо. Опубликованный график хранит снимки времени, ФИО, комнаты и этажа. Изменение справочников не переписывает подписанные документы.
  5. Одна точка валидации. ValidationService вызывается после генерации, после ручной правки и перед публикацией. Обойти её нельзя ни одним путём.
  6. Данные против кода. Этажи, факультеты, комнаты, смены, интервалы, правила — строки в таблицах. Enum остаётся только там, где новое значение требует новой логики.

Источник истины: актуальный roster

Архитектурное правило

Структура общежития определяет, какие помещения существуют. Актуальный roster определяет, кто фактически проживает. График строится только по актуальному roster. Исторический график использует собственный snapshot и никогда не зависит от последующих изменений состава.

Три разных понятия, которые легко слить в одно

Room / Block

Физическая структура. Существует независимо от заселения. 505А и 505Б есть в здании всегда, даже если в них никто не живёт.

Student

Фактически проживающий человек. Привязан к комнате, но комната не диктует, сколько таких записей существует.

Roster

Подтверждённый список проживающих на этаже. Единственный вход для генерации графика.

Как это устроено в данных

students ← рабочее состояние: кто живёт СЕЙЧАС │ целостность держат CHECK и FK │ каждая операция, меняющая СОСТАВ ▼ roster_versions ← неизменяемые версии состава └── roster_entries снимок каждого жильца на момент версии │ │ duty_schedules.roster_version_id ▼ duty_schedules ← график знает, по какой версии построен └── duties.*_snapshot и хранит ФИО/комнату/этаж отдельно
Текущий roster
Последняя версия со статусом confirmed. Её состав всегда совпадает с проекцией students WHERE floor_id = ? AND status = 'active' — это инвариант, проверяемый тестом и фоновой задачей.
Что создаёт версию
Добавление, удаление, переселение, перевод на другой этаж, деактивация, подтверждённый импорт. То есть всё, что меняет состав.
Что не создаёт
Правка атрибута: опечатка в фамилии, смена группы или факультета. Это идёт в audit_log, состав не меняется.
Историческая версия
superseded. Не редактируется никогда.

Ничего не применяется автоматически

Импорт никогда не пишет в students до подтверждения. Файл разбирается в roster_imports, diff показывается целиком, включая нераспознанные строки. Особо: «исчезнувший» студент по умолчанию не удаляется — администратор выбирает для каждого «деактивировать», «оставить» или «перевести на другой этаж». Отсутствие в файле может означать выселение, а может — что строку забыли внести.

Пустые состояния

Пустой блок или комната

Нормальное состояние. В генерации не участвует — из roster просто не приходит ни одного кандидата. В печатной форме отображается по настройке print_empty_rooms: в бланке 4 этажа пустые комнаты показаны, и это поведение сохраняется как опция, а не как правило.

Пустой этаж

Тоже корректное состояние данных. Но попытка создать график останавливается до генерации:

СлойКак обеспечено
БДВ rooms нет поля вместимости. roster_versions / roster_entries — append-only. duty_schedules.roster_version_id NOT NULL. duties.*_snapshot хранят ФИО, комнату и этаж независимо от текущих значений.
APIGET /floors/:id/roster отдаёт актуальную версию, а не обход комнат. Генерация принимает roster_version_id и не имеет параметра «взять всех из комнат». Импорт разделён на preview и apply.
АдминкаСтраница roster показывает версию и дату. Комнаты и блоки редактируются отдельно от состава — две разные страницы, чтобы «создать комнату» не читалось как «заселить».
ИмпортDiff с обязательным подтверждением, отдельное решение по каждому исчезнувшему студенту, нераспознанные строки блокируют применение.

TelegramПрофиль и график читаются по карточке студента. Деактивированный студент теряет доступ к боту; его прошлые дежурства остаются в архивных графиках, но новых он не получает.

-- ─────────── размещение ───────────
CREATE TABLE dormitories (
  id uuid PRIMARY KEY,
  number varchar(16) NOT NULL,              -- «4» → «общежития №4»
  name varchar(255),
  timezone varchar(64) NOT NULL DEFAULT 'Europe/Minsk',
  warden_name varchar(120),                    -- заведующий
  curator_name varchar(120),                   -- куратор
  council_head_name varchar(120),              -- председатель студсовета
  default_slot_template_id uuid,
  is_active boolean NOT NULL DEFAULT true
);

CREATE TABLE floors (
  id uuid PRIMARY KEY,
  dormitory_id uuid NOT NULL REFERENCES dormitories(id) ON DELETE RESTRICT,
  number smallint NOT NULL,                  -- сортировка и подстановка в заголовок
  code varchar(16),                            -- отображение, если этаж не число
  title varchar(120),
  print_min_rows smallint,                     -- ТОЛЬКО печать; NULL = без добивки
  print_empty_rooms boolean NOT NULL DEFAULT true,  -- ТОЛЬКО печать
  slot_template_id uuid NOT NULL REFERENCES duty_slot_templates(id),
  rule_set_id uuid NOT NULL REFERENCES duty_rule_sets(id),
  elder_student_id uuid,                       -- FK добавляется после students
  is_active boolean NOT NULL DEFAULT true,
  UNIQUE (dormitory_id, number)
  -- ВНИМАНИЕ: ссылки на faculties здесь нет и не будет
);

CREATE TABLE blocks (
  id uuid PRIMARY KEY,
  floor_id uuid NOT NULL REFERENCES floors(id) ON DELETE RESTRICT,
  code varchar(16) NOT NULL,                 -- «605»
  sort_order int NOT NULL DEFAULT 0,
  UNIQUE (floor_id, code)
);

CREATE TABLE rooms (
  id uuid PRIMARY KEY,
  floor_id uuid NOT NULL REFERENCES floors(id) ON DELETE RESTRICT,
  block_id uuid REFERENCES blocks(id) ON DELETE SET NULL,
  number varchar(16) NOT NULL,               -- «601», «605А» — буква часть идентификатора
  print_min_rows smallint,                     -- переопределение floors.print_min_rows
  sort_order int NOT NULL DEFAULT 0,
  is_active boolean NOT NULL DEFAULT true,
  UNIQUE (floor_id, number),
  CONSTRAINT block_on_same_floor CHECK (
    block_id IS NULL OR block_floor_id(block_id) = floor_id)
  -- ВМЕСТИМОСТИ НЕТ И НЕ БУДЕТ.
  -- Сколько человек живёт = COUNT(*) по students. Ноль — валидно.
  -- print_min_rows читает ТОЛЬКО ExportService.
);

-- ─────────── справочники ───────────
CREATE TABLE faculties (
  id uuid PRIMARY KEY,
  dormitory_id uuid REFERENCES dormitories(id),  -- NULL = общий
  code varchar(32) NOT NULL,                     -- «ФИТ», «ТОВ», любой
  name varchar(255),
  is_active boolean NOT NULL DEFAULT true,
  sort_order int NOT NULL DEFAULT 0,
  UNIQUE (dormitory_id, code)
);

CREATE TABLE study_shifts (
  id uuid PRIMARY KEY,
  dormitory_id uuid REFERENCES dormitories(id),
  code varchar(16) NOT NULL,                     -- «1», «2», «вечерняя» — что угодно
  title varchar(120),
  busy_from time, busy_to time,                    -- учебное время; NULL = неизвестно
  busy_weekdays smallint[] DEFAULT '{1,2,3,4,5,6}', -- в какие дни занят
  is_active boolean NOT NULL DEFAULT true,
  sort_order int NOT NULL DEFAULT 0,
  UNIQUE (dormitory_id, code)
);

CREATE TABLE duty_slot_templates (
  id uuid PRIMARY KEY,
  dormitory_id uuid REFERENCES dormitories(id),
  name varchar(120) NOT NULL,                    -- «Стандарт», «Сессия»
  is_active boolean NOT NULL DEFAULT true
);

CREATE TABLE duty_slot_rules (
  id uuid PRIMARY KEY,
  template_id uuid NOT NULL REFERENCES duty_slot_templates(id) ON DELETE CASCADE,
  weekday smallint NOT NULL CHECK (weekday BETWEEN 1 AND 7),  -- ISO
  slot_order smallint NOT NULL CHECK (slot_order > 0),
  time_from time NOT NULL, time_to time NOT NULL,
  label varchar(40),
  UNIQUE (template_id, weekday, slot_order)
  -- сколько смен в дне = сколько строк. Число 4 нигде не зашито.
);

CREATE TABLE duty_rule_sets (
  id uuid PRIMARY KEY,
  name varchar(120) NOT NULL,
  settings jsonb NOT NULL,                       -- см. раздел 7
  is_active boolean NOT NULL DEFAULT true
);

-- ─────────── студенты ───────────
CREATE TABLE students (

  room_id uuid NOT NULL REFERENCES rooms(id) ON DELETE RESTRICT,

  course smallint CHECK (course > 0),
  group_code varchar(16),
  telegram_id bigint UNIQUE,
  telegram_username varchar(64),
  link_code varchar(32) UNIQUE,                  -- одноразовый код привязки

Шаблон — это набор строк (день недели, № смены, время начала, время конца). Число смен в дне определяется числом строк и может отличаться от дня к дню.

Выбор шаблона — три уровня

dormitories.default_slot_template_id ← умолчание для новых этажей ↓ переопределяется floors.slot_template_id ← фактически используемый ↓ копируется при генерации duty_schedules.slot_template_snapshot ← неизменяемый снимок месяца
Почему снимок обязателен

Админ меняет время смен в октябре. Сентябрьский график уже подписан и висит на стене — он не должен измениться. Поэтому duties хранит собственные time_from/time_to, а duty_schedules — весь шаблон целиком в slot_template_snapshot. Печать берёт время из duties, а не из справочника.

Развёртывание календаря

expandMonth(template, year, month) → Slot[]

days = daysInMonth(year, month)         // Февраль 2028 → 29
for d in 1..days:
    wd    = isoWeekday(year, month, d)  // 1=Пн … 7=Вс
    rules = template.rules[wd]          // сколько есть — столько смен
    for r in rules:
        emit {date, slot_order: r.slot_order, from: r.time_from, to: r.time_to}

Единственное место в системе, где считается календарь. Високосный год обрабатывается стандартной библиотекой дат, не вручную.

Учебные смены и занятость

Учебная смена — справочник. Конкретные часы учёбы я не придумываю: их заполняете вы в /settings/study-shifts, и до заполнения правило просто не работает.

Модель занятости

ПолеТипСмысл
busy_fromtimeНачало учебного времени. NULL — неизвестно
busy_totimeКонец учебного времени
busy_weekdayssmallint[]В какие дни недели действует. По умолчанию Пн–Сб

Правило доступности

isAvailable(student, slot, ruleSet) → boolean

shift = student.study_shift
if shift is null or shift.busy_from is null:
    return true                         // нет данных — не ограничиваем

if isoWeekday(slot.date) not in shift.busy_weekdays:
    return true                         // в этот день студент свободен

overlaps = slot.from < shift.busy_to and slot.to > shift.busy_from

switch ruleSet.study_shift_mode:
    'ignore'           → return true            // смена не учитывается вообще
    'prefer_free'      → return true            // мягко: штраф в оптимизации
    'block_on_overlap' → return !overlaps      // жёстко: слот недоступен
    'require_consent'  → return !overlaps or student.allow_busy_slots
Значение по умолчанию

study_shift_mode = 'block_on_overlap'. Это отвечает вашей формулировке «нельзя автоматически назначать без разрешения/настройки»: пересечение с учёбой блокирует автоматическое назначение, но администратор может поставить студента вручную — тогда валидатор выдаст предупреждение, а не ошибку.

Пока busy_from не заполнен

Правило неактивно, и генерация работает так, будто учебной смены нет. Это не тихий сбой: на экране генерации показывается «Учебное время не задано для смен: 1, 2 — ограничение не применяется», со ссылкой на настройку. Иначе легко получить график, где первокурсник дежурит вместо пары, и не понять почему.

Режим require_consent

Промежуточный вариант на случай, если часть студентов готова дежурить в учебное время. Флаг students.allow_busy_slots ставит администратор — либо студент сам через бота («Готов дежурить утром»). Это единственное поле расписания, которое студенту разрешено менять, и оно расширяет, а не сужает его обязанности.

Алгоритм генерации

Правила не выведены из ваших документов

Приложенный график — пустой бланк. Все значения ниже — настройки со значением по умолчанию, а не найденные закономерности. Они лежат в duty_rule_sets.settings и меняются без изменения кода. Когда появится заполненный график за прошлый месяц, его можно будет прогнать через анализатор и предложить значения, соответствующие фактической практике.

Набор правил

{
  "duties_per_student":   "auto",          // auto | целое число
  "max_duties_per_day":   1,
  "min_days_between":     3,
  "study_shift_mode":     "block_on_overlap",
  "room_spacing":         "soft",          // off | soft | hard
  "block_spacing":        "off",
  "faculty_spacing":      "off",           // факультет не влияет на распределение
  "balance_by_slot":      true,            // поздние смены раскладываются равномерно
  "carry_over_balance":   true,            // учитывать нагрузку прошлого месяца
  "elder_exempt":         false,
  "exclude_non_active":   true,
  "excluded_dates":       [],
  "allow_quota_overflow": false,           // разрешить перебор при дефиците
  "max_load_spread":      1                // допустимый разброс дежурств, ±
}

Пайплайн

Выбран этаж ↓ Актуальный подтверждённый roster ← единственный источник кандидатов ↓ Только активные студенты ↓ Учебная занятость ↓ Матрица доступности ↓ Feasibility check ← стоп, если невозможно ↓ Генерация ↓ Validation ↓ Черновик + roster_version_id ↓ Проверка администратором ↓ Publish + snapshots
// ── 1. Календарь ──────────────────────────────────────────
slots = expandMonth(floor.slotTemplate, year, month)
slots = slots.filter(s => s.date not in rules.excluded_dates)

// ── 2. Пул: ТОЛЬКО из актуального подтверждённого roster ──
roster = rosterVersions.current(floor = F)      // status = 'confirmed'
if roster is null:
    return error('Состав этажа не подтверждён. Откройте список этажа.')

pool = roster.entries
    .where(student_status_snapshot = 'active')
    .where(not exemptDuring(month))
if rules.elder_exempt: pool = pool.without(floor.elder)

// Обхода rooms в пайплайне НЕТ. Пустые комнаты и блоки
// не участвуют — из roster по ним просто ничего не приходит.
assert pool.every(s => s.floor_id == F)   // нарушение = 500, не «почти ок»

// ── 3. Матрица доступности ────────────────────────────────
eligible = {}
for slot in slots:
    eligible[slot] = pool.filter(s => isAvailable(s, slot, rules))

// ── 4. Feasibility (раздел 8) — до распределения ──────────
report = checkFeasibility(slots, pool, eligible, rules)
if report.blocking: return report        // ничего не создаём

// ── 5. Квоты ──────────────────────────────────────────────
// pool.length > 0 гарантирован шагом 4 — деления на ноль не бывает
base  = floor(slots.length / pool.length)
extra = slots.length % pool.length
prev  = loadOf(pool, previousMonth)         // если carry_over_balance
quota = assignQuotas(pool, base, extra, prev)

// ── 6. Детерминированное распределение ────────────────────
// most-constrained-first: слоты с наименьшим числом кандидатов идут первыми
slots.sortBy(s => eligible[s].length)
for slot in slots:
    candidates = eligible[slot]
        .filter(s => assigned[s] < quota[s])
        .filter(s => respectsHardRules(s, slot, draft))
    if candidates.empty:
        // откат: снимаем мягкие правила по одному и пробуем снова
        candidates = relaxSoftRules(slot, draft, rules)
    if candidates.empty:
        draft[slot] = null; unassigned.push(slot); continue
    draft[slot] = argmin(candidates, s => cost(s, slot, draft))
    // cost учитывает: текущую нагрузку, интервал, соседей по комнате,
    // баланс поздних смен, пересечение с учёбой при prefer_free

// ── 7. Локальное улучшение ────────────────────────────────
draft = localSearch(draft, rules, maxIterations = 2000)
// парные обмены, пока уменьшается суммарный штраф

// ── 8. AI-оптимизация — опционально (раздел 18) ───────────
if rules.use_ai and aiEnabled:
    proposal = claude.rebalance(draft, pool, rules)
    draft    = validate(proposal).ok ? proposal : draft

// ── 9. Валидация и сохранение ─────────────────────────────
result = validate(draft, context)
save(schedule, draft, status = 'draft',
     slot_template_snapshot, rule_set_snapshot, dormitory_snapshot)
return {schedule, errors: result.hard, warnings: result.soft, unassigned}
Почему детерминированный алгоритм — основной

120 слотов на 25–45 студентов с квотами, интервалами и окнами доступности — классическая задача с ограничениями. Жадный проход most-constrained-first плюс локальный поиск решает её за миллисекунды, всегда одинаково и всегда валидно. Результат воспроизводим: одинаковый вход даёт одинаковый график, и это важно, когда админ спрашивает «почему тут Иванов».

Алгоритм не добавляет никого от себя

Кандидаты приходят ровно из roster.entries и больше ниоткуда. Ни структура комнат, ни прошлые графики, ни студенты других этажей не могут стать источником назначения. Если Сидоров выбыл из состава в октябре — в октябрьском графике его нет, даже если он дежурил весь сентябрь.

Незакрытые слоты

Если после всех попыток слот остался пустым, он сохраняется с student_id = NULL и попадает в список unassigned. График остаётся черновиком, публикация заблокирована, админ видит конкретные ячейки и причину. Пустой слот честнее, чем назначение с нарушением правил.

Правило публикации

POST /schedules/:id/publish возвращает 409, если есть хотя бы одна hard-ошибка. Кнопка «Опубликовать» в интерфейсе при этом неактивна, но проверка на сервере — не дублирование, а единственная настоящая гарантия.

V22 — черновик на устаревшем составе

Черновик сгенерирован, потом администратор подтвердил новую версию состава. Автоматически перегенерировать нельзя — можно затереть ручные правки. Поэтому это предупреждение с кнопкой «Перегенерировать по актуальному составу» и списком расхождений: кто выбыл, кто появился. Опубликованный график по V22 не проверяется никогда — он привязан к своей версии навсегда.

Soft-ошибки не блокируют

Разброс нагрузки, короткий интервал, соседи по комнате — это предупреждения. Реальность бывает такой, что идеального графика не существует, и админ должен иметь возможность опубликовать «как есть», видя список компромиссов. Они сохраняются вместе с графиком и показываются при открытии.

Система пропусков

Жизненный цикл

Дежурство не выполнено ↓ админ отмечает «Пропущено» duty.status = 'missed' violation.state = 'reported' ← ещё НЕ нарушение уведомление студенту ↓ ┌────┴─────────────────────┐ ▼ ▼ админ подтверждает признаёт уважительным violation = 'confirmed' violation = 'excused' counter += 1 duty.status = 'excused' │ в счётчик НЕ идёт ▼ counter == 3 ? │ да ▼ violation.state = 'explanation_required' sequence_no = 3 → уведомление студенту → уведомление администратору → запись в истории нарушений ↓ студент присылает объяснительную (текст или фото) ↓ violation.state = 'explained' ← админ принял

Ключевые правила

  • Пропуск не равен нарушению. Между reported и confirmed всегда стоит решение человека. Автоматически счётчик не растёт никогда.
  • excused не считается. Уважительная причина выводит дежурство из подсчёта полностью.
  • Порог настраиваемый. Тройка вынесена в violation_threshold, значение по умолчанию 3.
  • Окно подсчёта. Считаются подтверждённые пропуски за настраиваемый период — по умолчанию учебный год, не «за всё время». Иначе студент четвёртого курса обречён.
  • Повторное срабатывание. После explained счётчик не обнуляется; следующее срабатывание — на 6-м подтверждённом пропуске (кратно порогу). Это настройка threshold_mode: multiple | reset.
Нужно решение

Кто отмечает выполнение дежурства? Варианты: только администратор; администратор и староста; студент подтверждает сам, а неподтверждённое через сутки автоматически становится reported. Третий вариант резко снижает ручную работу, но требует доверия к самоотметке. От ответа зависит объём работы админа и часть логики MVP.

Замены и изменения

Правки делятся по статусу графика — и это принципиально разные вещи.

Черновик · draft

Правка меняет duties напрямую. Истории не создаётся — документ ещё не существует как документ. После каждой правки полная перевалидация.

Опубликован · published

Правка обновляет duties и добавляет строку в duty_changes. Эта строка печатается в таблице «Изменения в графике дежурств» — так бумажный документ остаётся сходимым с системой.

Запрос замены студентом

Студент: «Запросить замену» → указывает причину ↓ Бот показывает кандидатов СВОЕГО этажа, у которых нет дежурства в этот день и слот доступен ↓ Выбранный получает запрос → принимает или отклоняет ↓ Принял → на подтверждение старосте или админу ↓ Подтверждено → duty обновляется + duty_changes ↓ Оба студента получают уведомление

Без подтверждения староста подпишет бланк, не зная о замене. Поэтому шаг подтверждения обязателен, даже когда оба студента согласны.

Валидация не отключается

Любая замена — админом, старостой или по запросу — проходит через тот же validate(). Замена, нарушающая жёсткое правило, отклоняется с объяснением; нарушающая мягкое — принимается с предупреждением.

605А → 606. Закрывается student_placements, открывается новая строка. Прошлые графики печатают 605А, новые — 606.

Перевод на другой этаж

6 → 7. То же плюс смена students.floor_id. Сентябрьский график 6 этажа не меняется; в октябрьский студент попадает уже на 7-м.

Выселение

status = 'moved_out', left_at. Из пула генерации выпадает, из архивных графиков — нет.

Проверка правильности модели

Хороший тест на приёмке: сгенерировать сентябрь, опубликовать, выгрузить PDF, затем выселить одного из дежуривших, перевести другого на 7 этаж, заселить двух новых, изменить шаблон смен, переименовать факультет — и выгрузить сентябрьский PDF заново. Файлы должны совпасть побайтово, кроме даты формирования. После этого сгенерировать октябрь: выселенного в нём нет, новые есть.

Экспорт: PDF, XLSX, печать

Пайплайн

Данные + снимки ↓ DocumentModel — структура документа, независимая от формата ├─ meta общежитие, этаж, период, дата формирования ├─ approvals блоки подписей ├─ tableGroups строки с merge-указаниями └─ pagination разбивка на страницы и колонки ↓ ┌──┴──────────────┬──────────────┐ ▼ ▼ ▼ HTML-шаблон XLSX-writer (DOCX, 2-й этап) │ │ ├─ браузер: печать по Ctrl+P └─ headless: PDF

Просмотр в браузере, печать и PDF используют одну и ту же вёрстку. Расхождение между «как выглядит на экране» и «как вышло на принтере» исключено конструктивно.

Требования к PDF

Общие

  • Рендер headless-браузером, а не сборкой в PDF-библиотеке
  • Шрифт встраивается в файл — Times New Roman или PT Serif; иначе кириллица поедет на чужой машине
  • A4 portrait для обоих документов — как в оригиналах
  • table-layout: fixed + проценты ширин: колонки не могут уехать за правый край
  • overflow-wrap: anywhere — длинная фамилия переносится, а не растягивает таблицу
  • thead {display: table-header-group} — шапка повторяется на каждой странице
  • break-inside: avoid на группе строк одного дня и одной комнаты
  • Колонтитул: «стр. N из M» + «Сформировано DD.MM.YYYY»

Специфика двух документов

  • Оба — таблица в двух зеркальных блоках по 5 колонок
  • Список: merge комнаты на все её строки; merge факультета только при совпадении у всех жильцов
  • Список: строки берутся из roster-версии; комнаты из структуры — только для группировки и порядка
  • Список: пустые комнаты печатаются при print_empty_rooms; добивка до print_min_rows, если задано. Обе настройки — свойства печатной формы, а не данных
  • Список: комнаты делятся пополам между левым и правым блоком
  • График: merge даты на число смен этого дня
  • График: блок подписей повторяется на каждой странице
  • График: колонка «Подпись» всегда пустая
  • График: таблица изменений под каждой страницей, с колонкой «Подпись старосты»
  • График: разбивка считается в строках, а не в датах

XLSX

  • Настоящие merge-ячейки, повторяющие vMerge исходных документов
  • freeze_panes на строке шапки
  • Область печати: portrait, fit_to_width = 1, print_title_rows для повтора шапки
  • Границы, выравнивание, высоты строк — чтобы лист из Excel совпал с PDF
  • Даты и время текстом (01.09, 09:00-11:00) — иначе Excel их переформатирует

Интеграция AI

Границы

Claude не имеет доступа к БД, не выполняет инструментов записи, не публикует графики и не создаёт произвольных записей. Он получает срез данных в запросе и возвращает JSON, который целиком проходит ту же валидацию, что и ручная правка администратора.

Что отдаём Claude

Оправданно

  • Балансировка мягких критериев поверх уже валидного черновика, когда правил много и они конфликтуют
  • Объяснение дефицита человеческим языком: почему график не сходится и что стоит смягчить
  • Правила естественным языком: «первокурсников не ставить на 21:00–23:00» → структура rule_set на подтверждение админу
  • Импорт списков из произвольно свёрстанных Word/Excel файлов
  • Разбор объяснительных: краткое содержание и черновик решения; решение принимает человек

Только обычный код

  • Календарь, дни недели, високосные годы
  • Развёртывание сетки смен
  • Формирование пула этажа
  • Квоты и базовое распределение
  • Вся валидация
  • Feasibility check
  • Публикация, статусы, снимки
  • Счётчики пропусков и порог
  • Рендер PDF / XLSX
  • Права доступа и изоляция этажей

Обвязка

  1. В запрос попадают только студенты выбранного этажа — чужой student_id Claude физически неоткуда взять.
  2. Ответ парсится по схеме. Свободный текст не принимается.
  3. validate() — та же функция, что для ручных правок.
  4. Hard-ошибки → до 2 автоматических ретраев с текстом ошибок в промпте.
  5. После ретраев — фолбэк на детерминированный черновик. Статус остаётся draft, админ видит, что произошло и почему.
  6. Каждая попытка целиком пишется в ai_generations: запрос, ответ, ошибки, время.
  7. Публикацию нажимает человек. Всегда.
Порядок внедрения

AI — второй этап. Сначала детерминированный алгоритм, который заведомо даёт валидный график. Когда он работает и админ видит реальные компромиссы на живых данных, становится понятно, какие именно мягкие критерии стоит отдать Claude. Делать наоборот — значит оптимизировать вслепую.

Что блокирует разработку

Отделяю то, без чего нельзя начинать, от того, что можно решить дефолтом и поменять позже.

Блокирует

  1. Время учёбы каждой учебной смены. Значения busy_from / busy_to для 1-й и 2-й смены, и в какие дни недели они действуют. Без этого главное ограничение генерации не работает, и утренние смены 09:00–13:00 будут раздаваться вслепую. Не придумываю — нужны ваши цифры.
  2. Кто отмечает выполнение дежурства: только администратор, администратор и староста, или студент подтверждает сам с автоматическим переводом в пропуск через сутки. От этого зависит объём ручной работы, роль старосты и часть логики MVP.
  3. Сколько студентов и комнат на 6 и 7 этажах. 120 слотов на 25 человек и на 45 — разные системы. Нужно, чтобы feasibility показывал правду, а не пример.
  4. Есть ли на 6 и 7 этажах блоки (605 → 605А/605Б) или плоская нумерация комнат. От этого зависит структура печатной формы списка.

Можно начать с дефолтом

  1. Сколько строк на комнату печатать и показывать ли пустые комнаты. По умолчанию — по числу жильцов, пустые комнаты показывать. Бланк с пятью строками, как на 4 этаже, задаётся в print_min_rows.
  2. Гранулярность версий состава. По умолчанию новую версию создаёт любое изменение состава — добавление, переселение, деактивация. Если через месяц окажется, что версий слишком много, можно перейти на явную кнопку «Зафиксировать состав» и накопление изменений между фиксациями. Начинаю с автоматического варианта: он честнее и его проще ослабить, чем усилить.
  3. Дежурит ли староста наравне. По умолчанию да.
  4. Заголовок и колонтитул в списке — добавлять название этажа, дату и номера страниц или оставить точной копией оригинала. По умолчанию добавляю.
  5. Время отправки напоминаний и часовой пояс. По умолчанию Europe/Minsk, за сутки в 20:00 и в день дежурства в 09:00.
  6. Окно подсчёта пропусков — по умолчанию учебный год.
  7. DOCX-экспорт — по умолчанию не делаю, второй этап.
Про заполненный график

Принято: правила распределения не выводятся из пустого бланка и целиком живут в настройках. Когда появится заполненный график за прошлый месяц, отдельная утилита сможет прогнать его через анализатор и предложить значения rule_set, соответствующие фактической практике — сравнить нагрузку, интервалы, распределение поздних смен. Это не блокирует разработку и делается позже.

Почему экспорт списка идёт третьим, а не последним

M3 — самая ранняя точка, где результат можно физически положить рядом с вашим бумажным документом и сравнить. Если печать сходится, значит модель данных верна: комнаты, блоки, факультеты, смены, порядок и объединения. Если нет — исправлять надо сейчас, пока на модель не легли генерация, публикация и снимки. Откладывать экспорт на конец — самый дорогой способ узнать, что структура была неправильной.
